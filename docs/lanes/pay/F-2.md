# F-2 (F2b): transfers generate from approved work and monthly contracts (R3)

Draft from legacy code, 2026-11-05. Legacy source: `/home/user/studenthub` (master).

## Outcome (contract)
From W-2's confirmed payable inputs and active monthly-salary contracts, a "Generate" preview shows the lines it will create. Confirm creates them in one transaction (a late failure leaves zero lines). The weekly job does the same for auto-generate contracts for every company (fixes FI-F16, which stopped after the first), using D-FI2's period rule.

## Generation query (weekly job)
Contracts selected (CronController `actionWeekly`):
- `contract.type = TYPE_MONTHLY_SALARY`
- `contract.deleted = 0`
- `candidate.deleted = 0`
- `auto_generate = true`
- `start_date IS NULL OR DATE(start_date) <= CURDATE()`
- `end_date IS NULL OR DATE(end_date) >= CURDATE()`

Grouping: company = `parentCompany` if `parent_company_id` is set, else `company`. Candidates are grouped under that company's id.

Period: `start_date = today - 6 days`, `end_date = today` (rolling 7 days, not a calendar period). `noOfPayout = 4`. Currency hard-coded `"KWD"`.

## Rules
1. Monthly salary per payout: `candidate_total = contract.amount.candidate_total / noOfPayout` and `company_total` likewise (`common/models/TransferCandidate.php:1332-1334`). With 4 payouts this is salary / 4 per run, weekly.
2. Only the calculator in F-1 computes lines; the job does not compute money itself.
3. The job saves one transfer per company via `company\models\Transfer::saveTransfer` (the company-namespace model, not `common`). Confirm which model the company path uses before copying (both exist: `company/models/Transfer.php`, `common/models/Transfer.php`).

## Permissions
- Cron job runs without a user. Writes are as system.
- Manual generation is staff/admin only (controller auth; per-action checks not confirmed, see F-1 open item).

## Edge cases (legacy behaviour, verified in code)
- **FI-F16 bug, confirmed:** in `actionWeekly`, the loop `foreach ($data as $values)` contains `return \company\models\Transfer::saveTransfer(...)`. The first company returns and the loop ends, so only one company is generated per run. `CronLog::updateAll(... 'weekly')` after the loop is unreachable. The contract's fix is correct.
- **Rolling 7-day period.** Start is `today - 6`, end is `today`. With a Saturday-midnight run, periods are 7-day windows, not calendar months. Conflict with D-FI2 wording (see below).
- **Currency hard-coded to KWD** for every company, regardless of the contract currency.
- **Candidate ownership not checked here.** The contract join does not confirm the candidate still works for the company. Lock (F-3) refuses later, but the preview should flag it up front.
- **No idempotency.** Running the job twice in the same week creates a second transfer (no check against an existing transfer for the same company and period). Verify in `saveTransfer` before asserting; the `Transfer::saveTransfer` head (line 1182 onwards) was not fully read.
- **Silent when no contracts.** `$data` empty does nothing and writes nothing.
- **Contract `start_date` and `end_date` use DATE() of the stored value.** Timezone of the server is not checked here.

## Conflict with the settled decision (important)
- `contracts/finance.md` F-2 and D-FI2 say "monthly salary paid by calendar period, not salary / 4".
- `contracts/decisions-2026-10-27.md` row SHU-208 says: "Weekly auto-payout keeps salary / 4; rounding and rate selection (contracts overlapping the period) follow legacy ... The 12-month replay against legacy output is the acceptance test."
- Per the 10-27 rule (legacy is the benchmark, no regressions), the decisions file governs. Draft assumption: keep salary / 4 weekly with the legacy rolling window. Flag the finance.md text as stale. Do not re-ask Khalid.

## Test cases
1. Contract monthly 400.000, auto_generate true, active -> one weekly line of 100.000 per run.
2. auto_generate false -> excluded.
3. start_date in the future -> excluded; end_date in the past -> excluded; null dates -> included.
4. candidate.deleted = 1 -> excluded.
5. Two companies with monthly contracts -> BOTH produce a transfer in one run (regression test for FI-F16; legacy produces only one, so this test fails on legacy and is expected to pass on the rebuild; record as an intentional fix).
6. Parent company contract -> lines grouped under the parent company.
7. Preview equals the confirm result: same lines, same totals, zero side effects on preview.
8. Confirm with an injected failure on line N of M -> zero lines persisted (single transaction).
9. Run twice in the same period -> no duplicate transfer (legacy would duplicate; the rebuild needs an idempotency key, recorded as an intentional change unless the replay shows otherwise).
10. Replay: for a fixed week of legacy data, generated line totals equal legacy `transfer_candidate` rows to 3 dp.
