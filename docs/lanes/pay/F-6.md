Each paid line produces one notification event after commit (C3 feed now; email/SMS when C4 lands), never duplicated on retry.

## Edge cases
- **Inside the transaction.** `afterSave` runs during `save()`. In `TransferFile::process()` the save happens inside the DB transaction (line 245-260), so a notification would fire before commit. If the transaction later rolls back, the candidate is told they were paid when they were not. The contract requires "after commit". Legacy design would violate this if re-enabled as-is.
- **Duplicates on retry.** `afterSave` fires on every save where `paid` changed. A retried or re-run save that changes `paid` again (unpaid then paid) fires again. With the paid notification enabled and the file re-processed, duplicates are possible. The contract requires one event per line.
- **Unpaid notice fires on any unpaid change**, including admin corrections. Not requested in the contract; keep or drop as a recorded decision.
- **Mobile push and email share the same trigger.** No outbox table in legacy.
- **Tag filter** targets the candidate in the push system, not by device token. Confirm the C3 feed can express the same filter.

## Permissions
- Notifications are system-generated. No user action.

## Test cases
1. Line marked paid in a committed file -> exactly one paid event with the right amount and candidate.
2. Transaction rolled back after the line save -> zero paid events.
3. File re-run (already PROCESSED) -> zero new events.
4. Line unpaid then paid again -> one event per distinct payment (the contract key is the transfer_candidate id plus the confirmation id), not one per save.
5. Amount formatted to 3 dp in the message (`KD 12.500`).
6. Candidate with no device token -> event still recorded in the C3 feed, no error.
7. Candidate deleted or inactive between payment and send -> no send, event recorded as skipped.
8. Unpaid notice: admin correction to unpaid -> one unpaid event (or drop, per recorded decision).
9. Legacy parity: when the paid event is enabled, the message text equals the legacy string.

## Decision needed by rule (not by asking Khalid)
Legacy sends no paid notice today. The contract asks for one. Recommended: implement the paid event through an after-commit outbox (C3), with the legacy text, and record in the contract that this is a deliberate addition. Benchmark rule (no regressions) is not broken by adding a notice that legacy has in code but disabled; record the reason.
