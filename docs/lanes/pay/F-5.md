# F-5 (F3b): the bank's result is reconciled to lines, once (R3)

Draft from legacy code, 2026-11-05. Legacy source: `/home/user/studenthub` (master).

## Outcome (contract)
Finance uploads the bank's result file. One worker claims it with a lease (two workers never process one file; FI-F3). Lines are marked paid or rejected; transfers complete when all lines are paid. Notifications to people are queued after commit, never before. An ambiguous result is held for a person to decide.

## Claim and lease (legacy)
- `actionProcessTransferFiles` selects `status = PENDING` in batches of 100 and calls `process()` on each. There is no lease, no row lock, no `SELECT ... FOR UPDATE`, and no claim with a compare-and-set.
- `process()` sets `status = PROCESSING` and saves, but this is after the batch query has already read the row. Two cron runs overlapping (a slow run past one minute) can both read PENDING and both process the file. This is the FI-F3 risk the contract names.
- `CronLog` `last_ran_at` is updated only after the loop finishes.

## Processing rules (legacy `process()`)
1. Mark PROCESSING and save (line 182).
2. Begin DB transaction (line 194 region).
3. Parse by `bank` field:
   - `"BankStatement"` -> `populateFromBankStatement`.
   - any other non-empty value (AUB, KFH) -> `populateEntries`.
   - empty -> `populateEntriesForManual`.
4. Empty data -> rollback, `markFailed("no data")`, die (lines 213-222).
5. Load TransferCandidates by `tc_id` in the data. Any `tc_id` missing -> rollback, `markFailed('Invalid request')`, die (lines 225-240).
6. For each row: `paid = 1`, `transfer_file_id`, `transfer_confirmation_id` set, scenario `marking-paid`, save with up to 3 tries on deadlock (1213). Other save failures -> rollback, `markFailed($msg)`, die (lines 245-260). Other exceptions rethrown.
7. After the loop: for each transfer id in the data, `markTransferCompleteOnCandidatePaid` (line 290-300 region).
8. Commit, then `markProcessed(count, basename)` (line 316-320 region). Prod only: `Transfer::triggerPayableCandidateEvent()` (line 321-325).

## Parsers (result file formats)
- AUB result (`populateEntries`, `$this->bank == "AUB"`): one leading row removed, header is row 2. Empty `Status` rows skipped. Matches the candidate by `Credit Narrative` = `tc_id`. Confirmation id from `Status Description`. Debit narrative = transfer id.
- KFH result: 8 leading rows removed, header is row 9. Empty `Refrence Number` rows skipped (the header spelling `Refrence` is the bank's, keep it). Matches by `Beneficiary Account` (IBAN) + `Amount` = `candidate_total` + `Transfer Currency` + `paid = 0`, newest `tc_id` wins.
  - If no unpaid match: check for an already-paid line with the same IBAN, amount, currency and `transfer_confirmation_id` = `Refrence Number`. If found, the row is skipped silently (logged as duplicate).
  - If not found at all -> rollback, `markFailed`, die. The whole file fails.
- `BankStatement`: 2 header rows, match by `tc_id` (ignores invalid tc_ids silently, line 836).
- Manual: `populateEntriesForManual` (line 893).

## Edge cases (legacy behaviour, verified)
- **Overlap race (FI-F3):** described above. Real risk with a one-minute cron.
- **Silent loss on deadlock.** The retry loop `for ($i = 0; $i < 3; $i++)` with `continue` on 1213: after three deadlocks the loop exits without an error. The candidate is not marked paid, no failure is recorded, and the next row proceeds. The transfer may then complete later with a missing line or never complete. Rebuild must fail or retry the whole claim.
- **Stuck PROCESSING.** An uncaught exception inside `process()` (anything other than 1213) leaves `status = PROCESSING` forever. The cron selects only PENDING, so the file is never retried. No recovery path exists.
- **`die()` in a cron run.** `die()` after `rollBack()` ends the whole PHP process. Remaining pending files in the batch are not processed in that run. They wait for the next minute.
- **Whole-file failure on one unmatched row** (KFH and AUB). One bad line blocks all payments in the file. The contract's "held for a person to decide" is not legacy behaviour.
- **KFH match is heuristic.** Amount plus IBAN plus currency, newest id wins. A profile with two IBANs or two same-amount payouts can match the wrong line. The rebuild should match by the confirmation reference or by the tc_id written into the outbound file, and hold ambiguous cases.
- **Duplicate detection** for KFH relies on `transfer_confirmation_id` equal to the bank reference. Legacy AUB uses `Status Description` as confirmation id. Different fields for the two banks.
- **Currency default.** `currency_code` from body, then header `Currency`, default `KWD` (line 146-150 region).
- **Transfer amount at upload** is the sum at upload time. Lines changed later (rare) are not re-checked.

## Notifications
- `TransferCandidate::afterSave` (`common/models/TransferCandidate.php:327-341`): on `paid` change to PAID, `emailTransferSuccess` and `sendTransferPaidNotification` are COMMENTED OUT. `updateStats()` runs. So no paid notification is sent by legacy. See F-6.

## Test cases
1. Two workers claim one PENDING file -> exactly one processes it (lease). Legacy FAILS (no lease).
2. Cron overlap: run A and run B start in the same minute -> one processes; the other skips. (Legacy: both may process; test as a regression fixture.)
3. AUB file with 3 rows, all match -> 3 candidates paid, transfer completes only when no unpaid lines remain.
4. AUB row with unknown `Credit Narrative` tc_id -> whole file failed with `Invalid excel`, zero paid lines (legacy behaviour; rebuild may hold only that line; record choice).
5. KFH row matching two unpaid lines (same IBAN, amount, currency) -> newest picked by legacy; rebuild must hold as ambiguous.
6. KFH row already paid with same reference -> skipped, logged, no change.
7. KFH row not found -> whole file failed (legacy); rebuild holds the line.
8. Deadlock on the 2nd save of 3 -> retried; after 3 deadlocks -> file fails or line held (legacy silently skips; FAIL the legacy-style behaviour).
9. Uncaught exception mid-file -> file not stuck in PROCESSING: it returns to PENDING or to FAILED with an error (legacy leaves PROCESSING).
10. Re-running a PROCESSED file -> no change, no second paid event (idempotent).
11. Transfer with all lines paid -> status Distributing -> Complete; not before.
12. Empty file -> FAILED "no data".
13. Currency header default KWD when body missing.
14. Replay: a historical AUB and KFH file from legacy reproduces the same paid set and the same unmatched list.
