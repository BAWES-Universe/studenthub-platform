# F-4 (F3a, SHU-184): finance exports a bank file (R3)

Draft from legacy code, 2026-11-05. Legacy source: `/home/user/studenthub` (master). The bank format contract is SHU-220 (`docs/parity/bank-file-contract` on the studenthub-codex repo, not read in this pass).

## Outcome (contract)
From locked transfers, finance generates a bank file in the bank's format (SHU-220 contract), downloads it once per generation with an audit row, and the file records its lines. Regenerating the same set gives the same file (idempotent).

## Legacy source
- Plain-text payment advice, the main monthly export: `admin/modules/v1/controllers/TransferController.php:1971` `actionText()` (to about line 2030).
- Candidate selection: `common/models/TransferCandidate.php:775` `getPayableCandidateListFormat($currency, $offset, $limit)`, used by `actionText` (controller line 1981). A near-twin `getPayableCandidateAdvice` (line 869) builds the same rows with a different filter; it is not used by `actionText`.
- Audit row: `common/models/TransferBankAdvice.php` (table `transfer_bank_advice`, rules at lines 36-51: `tba_uuid`, `serial_no`, `created_by`, `file_path`, `is_deleted`).
- Other exports in the same controller, not read in full: xlsx payment advice (lines 1054-1060, 1504-1510, 1646-1652), txt for ABK (1899-1905, 1991-2003, 2042-2048). Each creates a new `TransferBankAdvice` row.
- Result file import (F-5) is `TransferFile::saveFile` (`common/models/TransferFile.php:140`).

## Output format (legacy `actionText`)
- Header `S1`: `S1,11622216,,MXD,M,,<d/m/Y today>,<dmY today>-01`. The account number `11622216` and `MXD` are hard-coded in the controller.
- Detail rows `D` (one per candidate), fields in order: `'Section Index' => 'D'`, `'Reference Number' => transfer_id` (debit narrative), `'Email ID' => candidate_email`, `'Invoice Date' => date('dmY')`, `'Invoice Info' => tc_id`, `'Invoice Currency' => transfer.currency_code`, `'Invoice Amount' => number_format(totalPaidToCandidate, 3, '.', '')`. Joined with commas, trailing comma per row.
- Footer `S3`: `S3,<count>,<total_amount 3dp>`.
- Batch id: `"T" . serial_no . "V1"`, where `serial_no = TransferBankAdvice::find()->count() + 1` (controller lines about 1982-1990). File name `<batch>.txt`.
- Written to `sys_get_temp_dir()`, saved to S3 (`transfer-bank-advice/`), then `sendFile` to the caller with a `filename` header.

## Fields recorded
- `transfer_bank_advice` row: `tba_uuid` (`tba_` + uuid), `serial_no`, `created_by` (admin id), `file_path` (basename of S3 object URL), timestamps, `is_deleted`.
- Lines are NOT stored per line in `transfer_bank_advice`. Per-line identity is the `tc_id` inside the file (Invoice Info column). The contract says "the file records its lines"; legacy records only the file, not line rows.

## Selection rules (what goes in the file)
Candidate query for `getPayableCandidateListFormat` (line 775): not read in full this pass. It is the one `actionText` uses. Its query is built from the same scopes as the twin below (`payable()`, `havingBankInfo()`, `activeCivilId()`, currency filter); read the body before porting and confirm the transfer-status filter. `getPayableCandidateAdvice` (line 869) builds the same query and adds explicit skips for: `candidate.bank` empty, no `bank_id`, no `transfer_benef_iban`, no `transfer_benef_name`, no invoice number, profile not completed. These skips are silent: nothing is reported. `getPayableCandidateListFormat` (line 775) applies its own filter; compare before porting.

## Permissions
- Admin bearer auth on the admin app. Per-action role check not confirmed (see F-1 open item). The download is available to any admin with access to the admin controller, as far as this pass shows.

## Edge cases (legacy behaviour)
- **Not idempotent.** Each call creates a new `TransferBankAdvice` with a new serial, new batch id (`T<n>V1`), and a header with today's date and `-01`. Regenerating the same set gives a different file. The contract requires the same file. Legacy does not do this; the rebuild must choose a stable batch key (for example on the set of tc_ids and the date of the batch) and record the change.
- **Pagination params.** `offset` and `limit` are request params; regenerating page 2 can overlap or skip rows if data changed between calls.
- **Silent drops.** Candidates without bank info or with incomplete profile are removed without a list. Finance cannot see who was skipped. The rebuild should report skipped lines (the contract says "the file records its lines").
- **Floats in total.** `$totalAmount += totalPaidToCandidate` (float), formatted at the end with 3 dp. Sum vs sum of formatted rows can differ at the fils. Make the footer the sum of the rounded row amounts, and test the difference.
- **Hard-coded account.** `11622216` and `MXD` are in the code. The rebuild must take them from config (X-1 typed configuration), and the value must match legacy's bank contract.
- **Duplicate download.** Nothing stops a second download creating a second audit row and a second batch number; the `serial_no` count is not locked (race on concurrent requests).
- **Other formats differ.** `actionDownloadPaymentAdvice` (line 2035) and `actionDownloadPaymentAdviceForAbk` (1591) use xlsx and other layouts. Not covered by this draft. Read them before the SHU-220 contract is closed.

## Test cases
1. Locked set of 3 lines -> file has 1 header, 3 `D` rows, 1 footer; footer count = 3; footer total = sum of rows at 3 dp.
2. Same set regenerated -> identical bytes (rebuild requirement; legacy FAILS: new serial and date).
3. Candidate without bank_id -> excluded from the file and listed in the skipped report.
4. Candidate with incomplete profile -> excluded and reported.
5. Mixed currency request (KWD and another) -> only the requested currency appears.
6. Transfer in Draft or Cancel -> no lines.
7. Transfer already Complete (all paid) -> no lines.
8. Amount 0.0005 rounding: row amount and footer agree with the bank format (replay of legacy output for a fixed set).
9. Concurrent generation of the same set -> one batch id (rebuild) or two audit rows with distinct ids (legacy).
10. Download writes exactly one audit row per generation and records the admin who generated it.
11. Replay: the rebuild's file for a historic legacy set equals the legacy file byte for byte, except the batch id and header date, which are recorded separately.
