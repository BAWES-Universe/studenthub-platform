## What "done" means for this lane

1. **Release matrix** (this PR). `tools/release-matrix/matrix.json` has one row for each of the 77 target screens and 7 exclusions in the SHU-235 contract, each of the 120 mobile endpoints, the seven import domains and the release steps. A gate closes only with evidence the check can parse (PR at an exact head, a run, or a run report comment); a waiver cites its decision record. `cli.js check` runs in CI through the test suite; `cli.js release candidate` must pass for the 17 Dec candidate; `release cutover` (adds K-6, K-7, PAY-SHADOW, SWITCHES) on 1 Jan; `release retired` (adds K-8) when legacy is switched off. The test also enforces SHU-235 section 7: deleting or duplicating any of the 382 legacy ordinals fails.
2. **Importer.** Order: M-4 catalogues and organizations with id maps, M-1 people, M-3 link report (`m4 linkreport`), M-2 documents, M-5 work, recruit and finance history (see the M-5 table map below), M-7 incremental, then M-6 full rehearsal. Each step is idempotent, writes a reconciliation report with legacy ids only, is tested on synthetic fixtures shaped like legacy, and closes its `built` and `dryRun` gates. `rehearsal` and `reconciled` close on the staging copy.
3. **Mobile exit.** Inventory done (below). The compatibility layer serves every `serve` route with the legacy shape in the 17 Dec candidate; `retire` routes answer with the legacy error shape; the legacy API is retired on 1 Jan, tested against traffic captured from a store build.
4. **Rollback.** K-5 rehearses final sync, single-writer cutover and rollback on staging before 17 Dec.

## M-4 catalogue map

`tools/legacy-import/src/m4-catalogue.ts` maps each legacy catalogue table; `PostgresCatalogueImportStore` (`@studenthub/db/import`) writes the items and the id map (`legacy_id_maps`, migration 0650). Names use the catalogue's own normalization. Legacy wall times are read as Asia/Kuwait. A re-run with the same rows writes nothing; a changed row is a conflict with both digests and is never overwritten.

| Legacy table | Catalogue kind | Rules |
|---|---|---|
| `country` | `country` | name `country_name_en` |
| `currency` | `currency` | name `title`, code `code`; `status` 0 imports as deleted; symbol and decimal places go to the currency details when valid |
| `bank` | `bank` | name `bank_name`; `deleted` imports as deleted; swift, IBAN bank code, ABK code and transfer type (`LCL` local, `SWF` international, `TRF` within bank) go to the payment details when valid |
| `tag` | `tag` | name `tag` |
| `brand` | `brand` | name `brand_name_en`; the brand's company link comes with organizations |
| `mall` | `mall` | name `mall_name_en` |
| `university` | `university` | name `university_name_en`; `deleted` imports as deleted |
| `area` | `area` | name `area_name_en`; no area details, because they need a governorate that legacy does not hold (reported per row) |

Two active rows of one kind whose names normalize the same become one item: the lowest legacy id is imported and the others map to it (reported as merged). For currencies and banks, a same-name row whose code or typed details differ (including details on one side only) is not merged: it is reported as `catalogue.nameConflict` and left for hand reconciliation. A later same-name currency or bank alias is checked against the target's item as stored (which a digest conflict may keep at older content), not just mapped by id; and any later alias maps only when the target's stored item is still active and of the same kind and name, otherwise it is held as `name_conflict`. An active platform item with the same kind and name that no legacy row holds yet is adopted rather than duplicated; a currency or bank is adopted only when its code and details match, otherwise it is refused as `name_conflict`, nothing is written, and a re-run refuses it again. Reconciliation is per table: legacy ids against the id map, with reported skips listed apart from unexplained gaps.

## M-4 organizations map

`tools/legacy-import/src/m4-organizations.ts` maps legacy `company` rows; `PostgresOrganizationImportStore` (`@studenthub/db/import`) writes the organization, its approved snapshot (`legacy_company_snapshots`, migration 0651) and the id map. `PostgresImportedOrganizationSnapshots` is the `ApprovedOrganizationAdapter` the organizations package reads; wiring it into the gateway replaces the unconfigured adapter and is the organizations owner's step (gateway wiring is outside this lane).

- A top-level company hangs under the operator organization in the registry, as an approved registration does; its snapshot parent is null. A sub-company's parent is its legacy parent through the id map, so parents import first.
- The platform allows one level of sub-company. A deeper company, one whose parent is missing, and one in a parent loop are reported and left out with their descendants.
- A company deleted in legacy (`deleted = 1`, which legacy's CompanyQuery hides) is an exclusion, reported as `company.archived`; its children are held as `company.archivedParent`. A company archived after it was imported keeps its organization and is reported, never deleted by the importer.
- At write time a child maps only under a parent whose stored organization is still top level, in the registry and in its snapshot; otherwise it is held as `parent_not_top_level` (a digest conflict can keep a parent legacy has since moved).
- The snapshot holds the columns the organization projections read (`company_name`, common names, descriptions, website, email, `currency_code`, approved to hire, hourly rate, bonus commission, status override) and the three activity counters, each normalized to what the package parses: blank text is null, decimals lose padding zeros, the currency code is upper case, and the status override is 0, 9 or 10. An unusable value becomes null and is reported by column; the company still imports.
- Stamped with the organizations package's parity revision, as `snapshotRow` requires.

## M-4 stores and brand links map

`tools/legacy-import/src/m4-stores.ts` maps legacy `brand` company links and `store` rows; `PostgresStoreImportStore` (`@studenthub/db/import`) writes `organization_brands` (migration 0200), `organization_stores` (migration 0202) and the id map (legacy tables `brand_company` and `store`). Companies, brands and malls import first; this step resolves them through the id map.

- Each legacy brand belongs to one company (`brand.company_id`), and the platform links each brand item to one organization. Two same-name legacy brands share one catalogue item: the first company's link is kept, and the other is refused as `brand_taken`, never moved. A link that is already in place for the same organization is adopted.
- A store keeps its legacy name and location trimmed. A blank name, or one longer than the platform's 120 characters, is reported as `store.badName` and left out, never cut to fit. A location longer than 500 characters is reported and imported as none.
- A store's brand must be its own company's, as in legacy's store form and the platform's stores screen. Another company's brand, an unknown brand and an unusable reference are reported and dropped from the store. At write time a brand that is not linked to the store's organization is refused as `brand_not_linked`.
- A store deleted in legacy (`deleted = 1`) imports as removed, with its last update time as the removal time, so later work and assignment history can still name it. `store_status` is not read: legacy sets it to 10 on every store and never reads it. The store manager is a sign-in role, so it comes with the grant import (M-3), not with contacts.
- Legacy times are Asia/Kuwait wall time. A row whose company, brand or mall has no id map row is refused by code (`no_organization`, `no_brand`, `no_mall`), and the batch goes on.

## M-4 contacts map

`tools/legacy-import/src/m4-contacts.ts` maps legacy `company_contact` links with their `contact`, `contact_email` and `contact_phone` rows; `PostgresContactImportStore` (`@studenthub/db/import`) writes `company_contacts` and `company_contact_channels` (migration 0402) and the id map (legacy table `company_contact`). Companies import first.

- The access contract decides the split. A link with `allow_access = 1` is a member who signs in: it imports as a grant once the person is linked (M-3), never as a contact, and is reported here as `contact.access`. A link with `allow_access = 0` becomes one contact. The column is a nullable boolean with default 0 (legacy migration `m210128_071555_role`), so only an explicit 0 or 1 is trusted: null, a missing column or any other value is quarantined as `contact.badAccess` and copies nothing. One legacy person on several companies gives one contact per company link. The mapper returns each link id in exactly one disposition (contact, access, quarantined, refused), so reconciliation counts by link id.
- Name and position (as the role title) are trimmed. A blank name, a name over 120 characters, or one with control characters is reported as `contact.badName` and left out. An unusable position is reported and imported as none.
- Email addresses: the person's sign-in address first, then the extra addresses oldest first. Phone numbers: oldest first. Each is normalized with the contacts screen's own rules, and repeats are kept once. An address or number the screen would refuse is reported and dropped. Past five of a kind, the first five are kept and the rest reported. An imported contact is one the screen could have saved.
- A contact deleted in legacy imports as removed, so it is never listed but the record of it stays. Legacy times are Asia/Kuwait wall time. A link whose company has no id map row is refused as `no_organization`, and the batch goes on. The import takes the contacts screen's company lock. A deleted person's removal time is the link's last update time, because legacy keeps no deletion time.

## M-1 people map (first slice: the approved profile snapshot)

`tools/legacy-import/src/m1-people.ts` maps legacy `candidate` rows, with the `country`, `university` and `area` names they point at, to the approved profile snapshot My profile reads for a linked person (`ApprovedProfileAdapter.readCandidate`, `projectApprovedProfile` in `packages/profile`). `PostgresPersonSnapshotImportStore` (`@studenthub/db/import`) writes `legacy_candidate_snapshots` (migration 0653) and the id map (legacy table `candidate`), with the M-4 contract: same digest unchanged, changed digest a conflict, never an overwrite. Mapper and store share one contract (`packages/db/src/import/person-snapshot-contract.ts`): exactly the projector's keys, scalar values, `candidate_id` equal to the row's canonical id, and a digest over the id and snapshot. The store checks it before any lookup, so an invalid row, new or replayed, is refused as `invalid` (naming only a canonical id) and the batch goes on. The table also requires the snapshot's `candidate_id` to equal its key. `PostgresImportedPersonSnapshots` is the snapshot port `PostgresLegacyLinkStore` reads, so a linked person's My profile shows the imported values, and a linked candidate with no snapshot yet reads as not imported. Wiring it into the gateway replaces the unconfigured source and is the profile owner's step (gateway wiring is outside this lane). The M-4 run (plan and write, through the same protected launcher, locks and receipts) carries M-1 as its last step, `candidate`, after contacts; the people step depends on nothing M-4 writes. The queue 13/14 contact columns are the next section.

- `M1_SOURCES` lists every column read. Credentials, tokens, email, phone, IBAN, the civil ID number, document locations and coordinates are never selected.
- The platform decides every value. Each column is kept only if the profile projector reads it without error, so an imported snapshot never makes a profile unavailable. Names also pass the self-edit name rule (outer spaces and runs of spaces are tidied first), and a birth date must give an age of at least 16 on the run date (Kuwait date). A value that fails is imported as not recorded with a reconciliation row (`candidate.nameRule`, `candidate.underMinimumAge`, `candidate.badValue`), never forced through and never dropped silently, as queue 13 requires.
- Unset legacy values (null, blank, `0000-00-00`, a 0 gender or driving-licence code, a 0 reference) are not recorded without a row. A country, university or area id missing from its table is reported as `candidate.unknownReference`. Legacy reads a candidate's university only where `deleted = 0`, so a university with any other marker (deleted, null or unknown) is not recorded (`candidate.inactiveReference`). A lookup id that names two rows once normalized is not recorded (`candidate.ambiguousReference`).
- A candidate id on more than one row (after trimming) is quarantined: every row of it is reported as `candidate.duplicateId` and none imported.
- Completeness is copied, not recomputed: `is_incomplete_profile` and `candidate_pending_profile` must agree (complete means an empty pending list); if they do not, neither is recorded and the row is reported as `candidate.completenessMismatch`.
- A candidate deleted in legacy (`deleted = 1`; a duplicate account is always also deleted) is an exclusion, reported as `candidate.archived`: legacy refuses its sign-in, so it can never be linked. Work and pay history (M-5) does not depend on this snapshot.
- Snapshots are ordered by legacy id and carry a digest of the id and values, so a re-run with the same rows gives the same digests (unchanged) and a changed legacy row is a conflict for the store, never an overwrite. `approvedSnapshotRow` adds the import time and the profile package's parity revision, as the projector requires.
- The plan identity binds the run's Kuwait date (taken once per run) and `M1_MAPPER_REVISION`, and the receipt shows the date. A write on another Kuwait day computes another identity and is refused as `planMismatch`, so it needs a fresh, reviewed plan: the minimum-age rule depends on the date. A candidate who turns 16 between two runs therefore gets a new snapshot digest: the next write reports a conflict for that id (a plan never reads the target), never an overwrite, and refreshing changed rows is M-7's.
- A snapshot is served only through the approved link (`legacy_account_links`, Q14-L): the importer never links a candidate to a principal by email or phone.

## M-1 people map (contact slice: phone, handle, civil ID)

`tools/legacy-import/src/m1-contact.ts` maps the queue 13/14 contact columns of the candidates M-1 imports (`mapLegacyCandidates(...).people`) to the values a linked person's profile takes at cutover: `person_profiles.phone` and `profile_handle`, and the Q14-3 civil ID (number, country, review flag). It is pure: no store, no run step yet.

- `M1_CONTACT_SOURCES` lists the columns read, all from `candidate`: `candidate_id`, `candidate_phone`, `profile_url`, `candidate_civil_id`, `candidate_civil_need_verification`. The legacy handle column is `profile_url` (queue 13's table calls it `candidate_profile_url`).
- Values pass the platform's own rules unchanged: the self-edit phone rule (a plus and 8 to 15 digits; an 8-digit local number becomes +965) and handle rule (lower case, 3 to 30 characters, starting with a letter), and `validateCivilId`. A value that fails is not recorded, with `contact.phoneRule`, `contact.handleRule` or `contact.civilIdRule`.
- The civil ID's country follows from its format: 12 digits is Kuwait, 9 is Bahrain. Queue 14 says "inferred from nationality", but legacy's country table has no ISO code and residents hold the civil ID whatever their nationality, so the number decides. **Q14 decision (recorded before any writer is wired):** the format is an issuer hint for the two supported schemes, not a verification; an imported civil ID keeps legacy's review flag and the platform's Q14-3 review rules, and nothing marks it verified because of its format.
- A signed or negative legacy value (a leading sign or dash, or a negative number) is `contact.civilIdRule`: it is refused before the shared formatter, which would strip the dash and leave digits. Interior separators (spaces, dashes) are allowed.
- Uniqueness matches the platform's partial unique indexes: a phone, handle or civil ID held by two imported people is recorded for neither (`contact.phoneDuplicate`, `contact.handleDuplicate`, `contact.civilIdDuplicate`), with a row on each person naming the other legacy id. Archived and duplicate-id candidates are not mapped and block nobody.
- The review flag is recorded only with a civil ID; a value that is not a legacy boolean is `contact.badValue`.
- The output holds personal values and stays in memory. Issues carry legacy ids, rule codes and column names only.
- **Store.** `PostgresPersonContactImportStore` (`@studenthub/db/import`) stages the values in `legacy_candidate_contacts` (migration 0654), apart from the person-owned tables, so nothing is shown to anyone yet. The civil ID number is stored only sealed by `CivilIdVault`, bound to `legacy-candidate:<id>` (not to a principal), with the vault's keyed hash. The row digest is an HMAC under a separate 32-byte key, so neither it nor any result can be used to guess a phone or a number; results carry legacy ids and refusal codes only. Same contract as the other imports: the closed row shape is checked before any lookup (`invalid`), same digest is unchanged, a changed row is a conflict and never an overwrite, a value another staged candidate already holds is refused as `duplicate` (unique indexes back the mapper's own duplicate rule), one savepoint per row, an advisory lock per batch. Any other failure rolls the batch back and throws only `PersonContactImportError` (`m1.contact.importFailed`, no detail, no cause), because a database or sealer error can carry values. `reconcile` is id coverage only: the run must also require no conflicts and no unexplained refusals.
- **Verified address (SHU-721).** The mapper also reads `candidate_email` and `candidate_email_verification`, and reads the address only when legacy marks it verified (1). It keeps it normalised: outer spaces trimmed, the trimmed input must be plain printable ASCII before any case change (so no non-ASCII spelling such as a Kelvin sign folds into an ASCII address), then only A-Z lowered; otherwise `contact.emailRule`, and a verified address two imported people share is `contact.emailDuplicate` for both. The store keeps only its HMAC (`verified_email_hmac`, migration 0655, under the same separate digest key, `emailDigest`), never the address. Agreed with the access lane: at cutover, for a linked person whose current address hashes to the staged HMAC, the cutover step inserts `principal_email_verifications` (verified true, source `legacy_import`) with `ON CONFLICT (principal_id, email) DO NOTHING`, so an OIDC answer, true or false, always wins; comms then reads the access lane's `emailVerifiedSql`. The compare is pinned to one rule: the step reads `principals.email` with the row locked `FOR SHARE` until commit, normalises it with `normaliseVerifiedEmail` (locale-invariant, null for a non-ASCII address) and inserts only when that equals the database's `principal_email_key(email)` for the same row and its HMAC matches. **One normalisation (migration 0658, GPT AMEND on #709):** `principal_email_key` is the same rule in SQL (spaces trimmed, plain printable ASCII under `COLLATE "C"`, then only A-Z lowered with `translate()`), and Access insertion (the OIDC record and veto), cleanup (the address-change trigger), the current-address trigger, the table's CHECK and `emailVerifiedSql` all use it instead of the locale-dependent `lower(btrim())`. An address with no key records nothing and never reads as verified, and a change to such a spelling drops the fact; for rows keyed by the old rule, an issuer negative still tied to the current address under it is carried to the current address's key and wins over any answer already there (`principal_email_verifications_rekey`, GPT AMEND 2), so a legacy promotion can never treat a vetoed address as unanswered; every other such row (a positive, a stale address, a current address with no key) is dropped, failing closed. A test checks the SQL and JavaScript rules agree over a corpus of ASCII and non-ASCII spellings.
- **Run step.** The M-4 run carries the contact slice as its last step, `candidate_contact`, after `candidate`, from the same `candidate` rows (M-4 reads `M1_SOURCES.candidate` plus `M1_CONTACT_SOURCES.candidate`; a password hash or bank detail is never read). Two keys come only from the operator's environment and are never written to a receipt, report, log or process argument: `M4_CONTACT_DIGEST_KEY` (plan and write; the HMAC key for row digests and verified-address HMACs) and `M4_CIVIL_ID_ENCRYPTION_KEY` (write only; the platform's civil ID key, which seals staged civil IDs). Each is canonical base64 of 32 bytes and they must differ, else `refused.contactKeys` before any read. Both live in the staging host's configuration and stay the same across runs: staged digests are kept, so a changed digest key turns every staged row into a conflict, never an overwrite. The plan identity binds each staged row as its legacy id and keyed digest (`personContactDigest`), never a plain hash of its values, plus the contact issues and `M1_CONTACT_MAPPER_REVISION`. A write needs migration 0656 and both tables.
- **Civil ID key check.** A well-formed but wrong civil ID key would stage ciphertext the platform cannot open, and a replay compares only digests. So the target holds a verifier (`legacy_import_target.civil_key_check`, migration 0656): a fixed, non-personal number sealed under the platform's key, bound to its own reference, set once and never changed (a trigger refuses any change). The operator provisions it once with `tools/legacy-import/m4 keycheck`, with `M4_CIVIL_ID_ENCRYPTION_KEY` taken from the staging gateway's own `CIVIL_ID_ENCRYPTION_KEY`; a later `keycheck` with the same key confirms it and another key is refused (`civilKey`). A write refuses before any step (`civilKey`) unless the supplied key opens the check. On a matching-digest replay the store also opens the staged civil ID and compares it with the row's number; if it does not open, the row is refused as `undecryptable` and never overwritten.
- **Promotion step.** `PostgresContactPromotion` (`@studenthub/db/import`) moves a linked person's staged values into the person-owned tables, one principal per transaction, under the per-principal lock the person's own profile, safe-write and authz writes take (`hashtextextended(principal, 5959)`), with the link row held `FOR SHARE` so an unlink waits. Only where the person has written nothing:
  - Phone and handle go into `person_profiles` only while that field's `written_at` is null. A cleared field is still written, so a person's clear is never undone.
  - The civil ID goes into `person_civil_ids` only when the person has no row at all (a released row is theirs too). It is opened from its `legacy-candidate:<id>` binding, its keyed hash re-checked, and re-sealed to the principal (revision 1, legacy's review flag kept, no expiry). A staged number that does not open, or whose hash differs, is `undecryptable` and nothing is written for it.
  - The verified address follows the access-lane agreement above: with the principal row locked `FOR SHARE`, the current `principals.email` is normalised in JavaScript with `normaliseVerifiedEmail`, must equal the row's `principal_email_key`, and is HMAC'd with the staging digest key; only on a match is a row inserted (verified true, source `legacy_import`), `ON CONFLICT DO NOTHING`. An address change in flight is waited for and the new address is judged.
  - A phone, handle or civil ID another person already holds is left with them (`taken`); the rest of that person's values still promote.
  - Outcome codes per value: phone and handle `promoted`, `none`, `personWritten`, `taken`; civil ID the same plus `undecryptable`; address `promoted`, `none`, `answered` (an OIDC or earlier answer exists and wins), `mismatch`, `unverifiable` (no address, outside the ASCII form, or the JavaScript and SQL keys disagree), `addressChanged` (the access lane's trigger refused; fail-closed, not expected under the row lock).
  - Each principal is promoted once: the same transaction writes `legacy_contact_promotions` (migration 0657) with the legacy id, `CONTACT_PROMOTION_REVISION` and the four outcome codes, and no value, digest or address. A later run skips them (`alreadyPromoted`), so nothing the person later clears or changes comes back. A person not linked yet, or linked before their row is staged, is skipped with nothing recorded (`notLinked`, `notStaged`) and a later run picks them up; `pending()` lists linked, staged, unpromoted principals.
  - Any other failure rolls that principal back and throws only `ContactPromotionError` (`m1.contact.promotionFailed`, no detail, no cause).
- **Promote run (`m4 promote`).** The operator runs it through the same launcher after a passing `write`. It names the accepted write it promotes from: `M4_ACCEPTED_WRITE` is that write's invocation and `M4_EXPECTED_PLAN` the plan digest the operator accepted. It checks the verified build (`provenance`, and only then binds revision, artifact and target); that `<accepted>.write.receipt.json` is a version-2 `write` receipt with status `ok`, the expected plan, the same target, revision and artifact, and a bound contact-set digest and digest-key fingerprint (`acceptedWrite`); the staging marker and target id (`target`); migration 0659 with the promotion table and `principal_email_key` (`promotionSchema`); both contact keys (`contactKeys`); that the digest key is the one the accepted write used, by its keyed fingerprint, before any per-person write (`digestKey`); and that the civil ID key opens the target's check (`civilKey`). It then takes the same one-writer lock as `write` (`writerBusy`), so a promotion never runs beside a write, and under that lock requires the staged contact set to equal the accepted write's digest exactly, so a partial, later or other write is never promoted (`stagedInput`). It reads no legacy data and needs no refresh lock. It walks `pending()` in batches of 500 on the writer session with a principal-id cursor (each batch starts after the last id seen, in C order), one transaction per principal, so skipped or repeated principals never stall the walk and it always ends; an id out of order fails the run (`m4.promoteOrder`). The separate `keycheck` receipt and the migration rollout stay operator stops before this step. The receipt (`<invocation>.promote.receipt.json`) holds the bound build and target and counts per outcome only (`promoted`, `skipped` by reason, and phone, handle, civil ID and address by outcome code), never a principal or legacy id; the per-principal record is `legacy_contact_promotions`. Exit 0 when every pending principal was handled, 2 when refused before any promotion, 1 when it failed part way (the receipt says `failed` with the counts so far and the fixed code, such as `m1.contact.promotionFailed`); each principal commits on its own, so a re-run promotes only the rest. People who link after cutover are picked up by the next `promote` run; promoting at link time needs the digest key in the gateway and is the profile owner's call.
- **Rollout and concurrent address writers.** Migration 0658 runs in one transaction (the migration runner wraps each file), and its `ALTER TABLE` takes an exclusive lock on `principal_email_verifications`, so a sign-in write or an address-change cleanup arriving during the migration waits, then runs under the new triggers and key; none runs half under the old rule. 0659 drops the one-off re-key once it has run (its test re-creates it from 0658's text in a rolled-back transaction). After that, a promotion and an address change serialise on the principal row (`FOR SHARE` in the promotion, the access lane's trigger for every other writer).

## M-2 documents map (first slice: where each document comes from)

`tools/legacy-import/src/m2-documents.ts` maps the four document kinds of the candidates M-1 imports to the legacy bucket keys that hold them: personal photo, CV, civil ID front and back (the platform's `CANDIDATE_DOCUMENT_ADMISSION` types; video is excluded, D3). It is pure: no storage read, no copy, no run step yet.

- `M2_DOCUMENT_SOURCES` lists the columns read, all from `candidate`: `candidate_id`, `candidate_personal_photo`, `candidate_resume`, `candidate_civil_photo_front`, `candidate_civil_photo_back`. M-1's snapshot never reads them.
- Keys follow legacy's own rules (`common/models/Candidate.php`, legacy main 55119d3):
  - Personal photo: a value under `candidate-profile-photos/` or `photos/` is the key. Otherwise legacy probes `candidate-profile-photos/<basename>`, then `photos/<basename>`.
  - Civil ID front and back: `photos/...` stays as it is, `candidate-civil-id/<x>` becomes `photos/<basename>`, and anything else becomes `photos/<value>`.
  - Photo and civil ID values are read as legacy reads them: PHP `trim`, then leading slashes removed.
  - CV: `candidate-resume/<value>`, the stored value verbatim. Only null or empty is no CV.
- A value that cannot name one object safely is `document.badKey` and is not recorded. That covers a non-string, a `.`, `..` or empty path segment, a backslash, a control or format character, or more than 960 bytes. A CV value with outer spaces or a leading slash is also held as `document.badKey`, never rewritten, because legacy keys it verbatim.
- One object, one owner. Every candidate row claims the keys legacy could resolve its values to, with legacy's own lenient rules and every probe, including archived, duplicate-id and unimported rows and rows with no usable id. An object any other row claims is recorded for no imported person (`document.sharedObject`, naming the lowest other usable legacy id, or none). Only the two first distinct claimants are kept per key, so a placeholder name shared by many rows stays cheap.
- Object names can hold personal words, so they stay in memory. Issues carry legacy ids, rule codes and column names only.
### M-2 document check (second slice: is each object there, admitted, and what it hashes to)

`tools/legacy-import/src/m2-document-check.ts` takes the mapped documents and checks each object in legacy's permanent bucket, read-only. Nothing is copied or stored.

- **Read-only port.** The bucket is reached through `LegacyObjectReader.read(key, maxBytes)`, which answers `found` with the bytes, `missing`, or `tooLarge`. It must read at most `maxBytes + 1` bytes and never write, copy or delete. This slice holds no credential and no bucket name. The adapter is a later slice: staging only, with credentials outside the repository.
- **Legacy's probe order.** The first key that holds an object is the object. A later key is never read once one is found.
- **Admission.** Each object passes the platform's own `validateCandidateContent`: a PNG or JPEG for a photo or civil ID, a PDF for a CV, 10 MB at most. The type is checked by content, never by name. A recorded document carries the key that held it (in memory only), its type, its size and its sha256.
- **Issues.** Each issue gives the legacy id, the column and one rule code, never a key, byte or error detail:
  - `document.missing`: no probed key holds an object.
  - `document.tooLarge`: the object is over the kind's limit.
  - `document.admission`: the object is not an admitted file for its kind.
  - `document.readFailed`: the read failed. Nothing is known about the object, so retry it later.
- **Memory and receipt.** Reads run one at a time, so a run holds at most one object in memory. `documentCheckCounts` gives the receipt's counts: documents checked, total bytes and a count per rule.

### M-2 bucket adapter and run input (third slice)

- **Bucket adapter** (`tools/legacy-import/src/m2-bucket.ts`, `legacyBucketReader`). It is the read-only adapter behind `LegacyObjectReader`:
  - It only ever sends GetObject. There is no list, put, copy, delete, ACL or presigned URL.
  - Each read asks for `bytes=0-<maxBytes>`, so the store sends at most `maxBytes + 1` bytes. The stream is cut once more than `maxBytes` arrive, whatever the store sends. An object whose stated total is over the limit is `tooLarge` without being read.
  - Only `NoSuchKey` is `missing`. A 403, an absent bucket or any other failure is a failed read, because S3 answers 403 for an absent key when the credential lacks ListBucket. The read credential therefore needs GetObject and ListBucket on this bucket only.
  - Below the limit an answer must be the whole object from offset 0. A malformed, nonzero or partial Content-Range, a full answer without a length, or a short, broken or bodiless answer is a failed read.
  - One deadline covers the request and draining its body, so a stalled body fails the read. Errors leave as a fixed message only.
  - Keys must have the mapper's shape: one of legacy's three prefixes, no path step, no control character. Any other key is refused before a request.
  - The bucket, region and credential come from the staging host's run environment, never from the repository.
- **Run input** (`tools/legacy-import/src/m2-run.ts`). Ownership is decided over every candidate row, so the input is proved complete before any object is read:
  - One statement reads every candidate row, with M-1's columns and the four document columns.
  - The table is counted before and after that read, and the read must match both counts (`m2.ownershipIncomplete`).
  - The run holds the refresh lock and binds the refresh identity, like `m4 plan`, so the input is one known generation.
  - `planM2` derives M-1's imported people and the documents to check from those same rows.
- **Run (`m4 doccheck`).** It runs through the same launcher, with a fresh `M4_INVOCATION`, `M4_REVISION`, `M4_ARTIFACT_DIGEST`, `M4_LEGACY_MIRROR_URL`, the refresh settings and the four `M4_LEGACY_BUCKET*` settings.
  - It checks the verified build (`provenance`) and the bucket setting (`bucketConfig`), then takes the refresh lock (`locked`) and binds an ok refresh identity (`refreshNotOk`).
  - It binds the refresh report to the copy it reads. An ok refresh records the lock file it held (`lock`), the mirror server and schema it copied into (`mirror.serverId` from `@@server_uuid`, `mirror.schema`), its per-table counts, and a fresh generation (`mirror.generation`). The refresh clears the mirror's one-row marker table `studenthub_refresh_generation` before it changes the mirror, and writes the new generation there only once the copy is counted, so a run that stops part way leaves no generation to match. A source table with that name refuses the refresh (`source.markerCollision`).
  - Doccheck refuses `lockMismatch` unless it holds that same lock file, `mirrorMismatch` unless the mirror it reads reports that server id and schema (two schemas on one server share a server id), and `generationMismatch` unless the mirror's marker holds exactly one row with the report's generation.
  - It reads the whole candidate table, refusing `ownershipIncomplete` unless the counts agree, and `staleCount` unless the rows read equal the refresh's candidate count. It then maps with `planM2` on the run's Kuwait date.
  - A refresh report without that provenance (from before it) still runs, but its receipt and report carry `documents.diagnostic: true`, which never authorizes a copy; refresh again first.
  - Only then does it read each object once through the adapter. A failed object read is counted as `document.readFailed`, not a run failure.
  - It needs no database or key, writes nothing to any database and copies nothing.
  - The private report (`<invocation>.doccheck.report.json`, mode 600, staging host only) lists each checked document's legacy id, kind, type, size and sha256, and each issue's legacy id, column and rule. It never holds a key, name or byte.
  - The receipt holds the bound build, the refresh and the date, plus counts per rule and `documents.set`: a digest over the checked documents' ids, kinds, types, sizes and hashes, which the copy step must find again.
  - Exit 0 when the report was written, 2 when refused before any object read, 1 when failed.
- **Next slices (proposed):**
  - The copy step: read each object again and refuse it unless it still hashes to the recorded sha256. Stage it apart from the person-owned documents, bound to `legacy-candidate:<id>` like the contact slice.
  - Promote it into the person's slot on link, only where the slot is empty. The check and the write happen under the owner and slot lock, and a slot the person cleared on purpose counts as theirs: the import never refills it.
  - Legacy's public objects stay where they are until SHU-54 is fixed.

## M-3 identity link report

Q14-L gives each person a self-service link (legacy sign-in) and staff a manual one. M-3 adds the bulk report staff follow up from (`readLinkReport`, `@studenthub/db/import`; `tools/legacy-import/m4 linkreport`). Links stay keyed by principal and legacy id, never by email, and nothing here links anyone.

- **Rules.** Each lists legacy candidate ids, in numeric order, each id once. Ids follow the link tables' own contract (positive digits, any length, migration 0215), which contains the import's 1 to 18 digit form, so a valid link row with a longer id is listed like any other and never fails the report:
  - `link.unlinked`: an imported candidate (`legacy_candidate_snapshots`) no principal is linked to yet.
  - `link.notImported`: a link to a candidate the import does not carry (archived or quarantined in legacy, or not imported yet), so the person sees no imported profile.
  - `link.multiplePrincipals`: historical links only: a candidate whose link history (`legacy_account_link_events`, kind `linked`) names more than one principal, for example linked, unlinked and then linked to someone else. One person relinking is not counted. This is the contract's "offered to more than one person" as far as the platform can observe it; an offer nobody accepted leaves no record and is not counted.
  - `link.contactTaken`: a promoted person whose staged phone, handle or civil ID another person already holds (`legacy_contact_promotions` outcome `taken`).
  - `link.emailMismatch`: a promoted person whose current address did not hash to the candidate's verified legacy address, or changed under the promotion (`mismatch`, `addressChanged`), a sign the link may name the wrong person.
- **Reading.** One read-only, repeatable-read transaction on the target, so the lists and totals describe one moment. It reads ids and outcome codes only: no name, contact value, digest, address or principal id. Any failure is `m3.link.reportFailed`, with no detail.
- **Run (`m4 linkreport`).** Through the same launcher, with a fresh `M4_INVOCATION`, `M4_REVISION`, `M4_ARTIFACT_DIGEST`, `M4_TARGET_ID` and `M4_DATABASE_URL`. It checks the verified build (`provenance`), the staging marker and target id (`target`) and migration 0659 with the snapshot, link, link-event and promotion tables (`schema`). It needs no key, reads no legacy data, takes no refresh or writer lock and writes nothing to the database. The private report (`<invocation>.linkreport.report.json`, mode 600, on the staging host only, never attached anywhere) holds the ids by rule; the receipt holds the bound build and target, the imported and linked totals and a count per rule only. Exit 0 when the report was written, 2 when refused, 1 when the read failed.

## M-4 run on staging

`tools/legacy-import/src/m4-cli.js` runs all of M-4 against the refreshed legacy copy. A Hermes card runs it on the staging host only through the operator entry `tools/legacy-import/m4 plan|write`, a shell script that starts Node with a cleared environment and no flags and runs the launcher `tools/legacy-import/m4-launch.mjs`. The launcher verifies the runtime before any importer module loads. The importer module is not an entry point: run directly, it evaluates its imports but never calls `main`. Every control below is in the repository; no other wrapper is needed.

- **Invocation.** Every run is named by `M4_INVOCATION`, a fresh UUID, and owns its own files in `M4_OUTPUT_DIR` (default `/var/lib/legacy-import/m4`): `<invocation>.<mode>.receipt.json` and `<invocation>.<mode>.report.json`. It first claims the name by creating `<invocation>.claim` exclusively. A reused name is refused (`refused.invocationUsed`) and touches nothing. After the claim, every outcome, refusals included, tries to publish a terminal receipt for that invocation. If that write itself fails, the receipt may stay `started` or be absent; see "No terminal receipt" below.
- **Pass rule.** A write passed only when `acceptWrite` holds: that invocation's own terminal receipt says `ok` for the expected plan, and that same invocation exited 0. An older receipt, even for the same plan, never counts.
- **No terminal receipt.** If an invocation's receipt still says `started`, or the invocation exited non-zero for any other reason (for example the output directory became unwritable after some batches committed), it is not a pass. It also does not prove that nothing was written. The operator treats the target as partly written and, on the same Kuwait date as the plan, retries the same reviewed plan with a fresh `M4_INVOCATION`. After Kuwait midnight the plan's identity no longer matches, so the operator makes and reviews a fresh plan instead; rows already committed are never overwritten, and a date-dependent change to one of them is reported as a conflict. Every step is idempotent: rows already written report `unchanged` and only missing rows are written. Only that retry's own `ok` receipt with exit 0 is a pass.
- **Refresh lock.** The CLI takes a shared, non-waiting `flock` on `LEGACY_REFRESH_LOCK` and holds it until it exits. It reads `last-run.json` and every legacy table under it. A refresh holding the lock makes the run refuse (`refused.locked`).
- **Writer lock.** A write also takes the target database's one-writer lock: a session advisory lock on its own connection, independent of the refresh lock. It is taken before the first write and held until the terminal receipt is published, across every batch. A second writer on the same database is refused (`refused.writerBusy`).
  - Every import transaction runs on that same session (`WriterSessionPool`), and each checkout first re-checks there that the lock is still held. The lock is checked once more immediately before the outcome is published. That check and the receipt file write are not one atomic step.
  - Waits on that session are bounded (`lock_timeout` 60s, `statement_timeout` and `idle_in_transaction_session_timeout` 15 min). A batch blocked by another transaction rolls back and the run ends `failed`, rather than holding both run-wide locks indefinitely.
  - If the session is lost, the transaction in flight dies with it and no later batch starts. The run ends `failed` with `m4.writerLost`, and the receipt separates confirmed from unconfirmed steps.
- **Build provenance (launcher, before the importer loads).** The launcher uses node builtins only.
  - **Pinned runtime, clean start, outside JavaScript.** The operator entry `tools/legacy-import/m4` starts the checkout's own Node runtime, `.runtime/node/bin/node`, never a `node` found on `PATH`. That runtime is the exact release in `tools/legacy-import/node-runtime.txt` (version, platform, sha256 of the official archive), installed by `tools/legacy-import/install-runtime.sh`, and its bytes are part of the digest. Before Node starts, the entry removes every environment variable except the M-4 settings listed in it, sets `PATH` and `LANG` itself, and passes settings only in the environment, never as process arguments. Node gets no flags, so no `NODE_OPTIONS`, `NODE_PATH`, preload or loader setting reaches it. As a second line, the launcher refuses (`refused.startup`) if Node has any flag or such a setting, and refuses (`refused.provenance`) unless the binary running it is the checkout's pinned runtime. A startup hook runs before any script, so the in-script checks cannot stop one; the entry script is what prevents it.
  - **Commit.** The checkout is a git checkout whose HEAD is `M4_REVISION`, with no tracked file changed and no untracked file outside `.gitignore`, so the launcher and the entry script are the reviewed ones.
  - **Digest.** Every file and symlink in the checkout outside `.git` (sources, built `dist` trees, every `node_modules` tree wherever it sits, the lockfile, the pinned Node runtime; file bytes and symlink targets), together with the platform, architecture and Node major version, hashes to `M4_ARTIFACT_DIGEST`. Anything extra, such as a dependency tree under a workspace, an ignored `.env` or a stray file, changes the digest.
  - **Protected runtime.** The user running the launcher cannot change the verified tree: it is not root; it owns no file, directory or symlink in the checkout and no directory on the path to it; nothing in the checkout has a write bit; no directory on the path is writable by group or others (so not under a world-writable directory such as `/tmp`). Every symlink is relative and resolves to something hashed: inside the checkout and never into `.git` or npm's install record, which the digest skips. The same holds for git's store: `.git` must be a directory, not a `gitdir:` file; nothing in it may be a symlink, owned by that user or writable; it may hold no `commondir`, `gitdir` or object `alternates` file, which would make git read another store; and its config may have no `include` or `includeIf` section. git then runs with no global or system config, `core.fsmonitor=false` and hooks disabled. The launcher checks all of this before it runs git at all, so git never reads config, hooks or an fsmonitor setting that user could have written. So between hashing and loading, only the tree's owner (root on the staging host) could change it.

  Any failure, or a runtime file that cannot be read, refuses with `refused.provenance`. Nothing is loaded and no receipt is written: there is no receipt, so no pass. The importer re-checks the verified provenance it is handed against the pins.
  - The pinned digest comes from an independent build. The workflow "M-4 importer build pin" checks out the exact commit (the pull request head, or the pushed `main` commit), installs the pinned runtime, runs `npm ci --ignore-scripts` and `npm run build` with it, with nothing run first, and prints `m4 provenance source=<push|pull_request> head=<commit> clean=<…> platform=<os-arch-nodeN> node=<version> runtime=pinned artifact=<digest>`. The step passes only for a clean, complete build whose HEAD is the declared commit, made by the pinned runtime, with every link resolving to a hashed file (`links=inside`), so a pin is never issued for a build the launcher would refuse. Every run then packages that build and smoke-tests the package credential-free the way staging runs it: check the sum, unpack it as root under `/srv` with `--no-same-owner`, `chmod -R a-w`, and run `tools/legacy-import/m4 plan` as `nobody` with the pin's revision and digest. It must verify and stop at the importer's `refused.invocation`, before any connection.
  - For a `main` push the same run keeps that exact build as the artifact `m4-runtime-<commit>` (30 days): the whole checkout as a tarball, its sha256 and the pin line. The build is fully determined by the commit: the pinned runtime, the lockfile and the platform. Independent builds match: at `a16205aa` and `6655bfbd`, fresh local builds gave the same digests as the hosted runs.
- **Reading.** It reads only the tables and columns listed in `M4_SOURCES`, one `SELECT JSON_OBJECT(...)` per table, through the walker's read-only mirror reader. It refuses unless the last refresh says ok.
- **Plan identity.** A sha256 over:
  - the stated revision (`M4_REVISION`);
  - the runtime digest the launcher verified (the whole checkout outside `.git`, with platform and Node major version);
  - the refresh identity;
  - the destination as supplied: `M4_TARGET_ID` and `M4_OPERATOR_ORG_ID` (the operator parent that top-level organizations are written under). `plan` does not connect to the platform database, so it binds the target id it is given without checking it; `write` checks the observed `legacy_import_target` marker and the operator organization against these values before any write;
  - the run's Kuwait date, `M1_MAPPER_REVISION` and `M1_CONTACT_MAPPER_REVISION`;
  - the number of rows read from each legacy table;
  - every mapped row's legacy id and digest (for the contact step, the HMAC under `M4_CONTACT_DIGEST_KEY`, so the identity cannot be used to guess a phone, handle, civil ID or address);
  - the reconciliation: every issue's rule, legacy table, legacy id (`?` when it has none, counted by multiplicity), column and related legacy id, as a sorted list. Never a value.

  A change to any bound field (revision, runtime digest, refresh identity, target, operator, date), to a table's row count, to the ordered list of mapped rows' legacy ids and digests, or to the issue list gives a new identity. So a row the mappers set aside, or a value that newly fails a rule, cannot change what the reviewer approved while every mapped digest stays the same.
- **`plan`.** Maps every table and writes nothing to the platform. Its receipt shows the plan identity and everything it binds.
- **`write`.** Refuses before any write unless:
  - `M4_EXPECTED_PLAN` equals the identity it computes now (`planMismatch`);
  - the database's `legacy_import_target` row says `staging` with `target_id` equal to `M4_TARGET_ID` (`target`, migration 0652);
  - the operator organization exists there (`operator`);
  - migration 0656 is recorded there and the `legacy_candidate_snapshots` and `legacy_candidate_contacts` tables exist (`schema`), so an older target refuses before any step instead of failing at the last steps after the others committed;
  - `M4_CIVIL_ID_ENCRYPTION_KEY` opens the target's provisioned civil ID key check (`civilKey`);
  - no other writer holds the database (`writerBusy`).

  Then it publishes `started` and imports in dependency order: catalogues, companies, brand links, stores, contacts, people, person contacts. Each step is idempotent.
- **Receipts.** Counts and rule codes only, never a legacy id or value. Each file is written whole (temporary file, then rename) with mode 600. The status is one of:
  - `started`;
  - `ok`;
  - `refused_rows`;
  - `failed`;
  - `refused`, with a fixed code.

  A `failed` receipt lists the confirmed steps (written, and their results checked) and the unconfirmed ones. The first unconfirmed step may have committed in part.
- **Report.** Private, mode 600, never attached to a pull request. Per step it holds legacy and mapped counts, issue counts and legacy ids by rule, and the write results. `receiptSafe` re-checks every field before the file is written. Errors print fixed codes only.
- **Refusal codes.** Launcher: `startup`, `provenance`. Importer: `usage`, `invocation`, `invocationUsed`, `revision`, `destination`, `writeConfig`, `provenance`, `locked`, `contactKeys`, `refreshNotOk`, `planMismatch`, `target`, `operator`, `schema`, `civilKey`, `writerBusy`, and for promote only `acceptedWrite`, `digestKey`, `stagedInput`, `promotionSchema`.
- **Exit codes.**
  - 0: ok.
  - 3: a write step refused rows or found conflicts.
  - 2: refused before any write.
  - 1: failed.
- **Operator steps (Hermes card, staging only).**
  - **Once, after migration 0652 is applied:** `INSERT INTO legacy_import_target (environment) VALUES ('staging') RETURNING target_id` on the staging database, and record that `target_id` (not a secret). No other database gets the row. Then, once migration 0656 is applied, run `tools/legacy-import/m4 keycheck` with a fresh `M4_INVOCATION`, `M4_REVISION`, `M4_ARTIFACT_DIGEST`, `M4_TARGET_ID`, `M4_DATABASE_URL` and `M4_CIVIL_ID_ENCRYPTION_KEY` set to the staging gateway's `CIVIL_ID_ENCRYPTION_KEY`, all from the staging host's configuration; its receipt says ok with the check set. **Who and how:** only an authorised staging operator runs it, through a Hermes card, with the key read from the gateway's own configured `CIVIL_ID_ENCRYPTION_KEY` on the staging host (never typed into a card, never from another source). The receipt (`<invocation>.keycheck.receipt.json`) is the non-sensitive record: status, target id, the verified revision and artifact digest, and no key. A first `keycheck` with an arbitrary key would prove only continuity, not that it is the gateway's key, so this provenance is the trust boundary: no staging write is approved without a `keycheck` receipt that says ok for the same target, made by a pinned artifact from the deployed commit. This revision writes only to a database whose marker row says `staging` with that `target_id`: migration 0652 accepts only `staging`, and the CLI requires `environment = 'staging'` and the matching id. The CLI does not otherwise tell which database `M4_DATABASE_URL` reaches. So the guarantee depends on that marker row existing only on the staging database: no other database may be restored from a staging dump or given a copy of the row, and `M4_DATABASE_URL` comes only from the staging host's configuration. Enabling the production cutover needs a later code and schema change, reviewed, plus the owner's explicit go.
  - **Each rehearsal:**
    0. Confirm the target's `keycheck` receipt exists, says ok, and that its `target`, `revision` and `artifact` match this target and the approved deployment. A missing or mismatched receipt is an **operator stop**: do not plan or write. Do not rely on the CLI to catch it. A write refuses with `civilKey` only when no verifier is stored or the key does not open it, so it can pass when a verifier already exists even though the receipt is missing. The receipt shows what ran, not where the key came from; sourcing the key from the staging gateway stays the operator's duty.
    1. Take the `artifact=` digest from the "M-4 importer build pin" run for the `main` push of the deployed commit. Use only a line with `source=push`, `head=` equal to the deployed commit, `clean=true`, `runtime=pinned`, `links=inside` and `platform=linux-x64-node22`, from a successful run. A `source=pull_request` line is never used.
    2. As root, put that exact build under a root-owned path that only root can write, such as `/srv/m4/<commit>`. Preferred: the artifact `m4-runtime-<commit>` from that same run. Check its `SHA256SUMS`, then unpack it with `tar -xzpf <tarball> --no-same-owner`. Otherwise, clone the commit there and run `sh tools/legacy-import/install-runtime.sh`, then `npm ci --ignore-scripts` and `npm run build` with `PATH` starting at `.runtime/node/bin`. Either way, then `chmod -R a-w` the checkout. It stays owned by root, and the launcher refuses it unless it hashes to the push digest.
    3. As an unprivileged service user that owns nothing in that path (not root), run `tools/legacy-import/m4 plan` with a fresh `M4_INVOCATION`, `M4_REVISION`, `M4_ARTIFACT_DIGEST`, `M4_TARGET_ID` and `M4_OPERATOR_ORG_ID`. Also set `M4_CONTACT_DIGEST_KEY`, `M4_LEGACY_MIRROR_URL` (the read-only mirror account), and `LEGACY_REFRESH_REPORT` and `LEGACY_REFRESH_LOCK` unless the defaults apply. These come from the staging host's existing configuration, never from the card text, and no receipt records them. That user needs write access only to `M4_OUTPUT_DIR` and read access to the refresh lock and report.
    4. Review its receipt and its private report (on the staging host only, never attached anywhere): the counts, the excluded rows by legacy id and rule, and the issues. Approve the plan identity only after both.
    5. Run `tools/legacy-import/m4 write`, as the same user, with a new `M4_INVOCATION`, the same settings, and `M4_EXPECTED_PLAN` set to the reviewed `plan`. Also set `M4_DATABASE_URL` (staging PostgreSQL), `M4_IMPORT_ACTOR` (sha256 hex of the operator identity) and `M4_CIVIL_ID_ENCRYPTION_KEY` (staging's civil ID key), all from the staging host's configuration.
    6. Report a pass only by `acceptWrite` on that write invocation's receipt and exit code.
    7. After a passing write, run `tools/legacy-import/m4 promote` as the same user with a new `M4_INVOCATION`, the same `M4_REVISION`, `M4_ARTIFACT_DIGEST`, `M4_TARGET_ID`, `M4_DATABASE_URL` and both keys from the staging host's configuration, plus `M4_ACCEPTED_WRITE` (the passing write's invocation) and `M4_EXPECTED_PLAN` (the plan digest accepted for it). No other write may run in between; if one did, promote refuses `stagedInput` and the newer write is the one to accept. Report its receipt's counts only; a `failed` receipt is retried with a fresh `M4_INVOCATION`.
    8. After a promote, or whenever staff ask, run `tools/legacy-import/m4 linkreport` as the same user with a new `M4_INVOCATION`, the same `M4_REVISION`, `M4_ARTIFACT_DIGEST`, `M4_TARGET_ID` and `M4_DATABASE_URL`, and no keys. Report its receipt's counts only; staff read the ids from the private report on the staging host.
    9. For M-2, run `tools/legacy-import/m4 doccheck` as the same user with a new `M4_INVOCATION`, the same `M4_REVISION` and `M4_ARTIFACT_DIGEST`, `M4_LEGACY_MIRROR_URL`, and the refresh settings. Also set `M4_LEGACY_BUCKET`, `M4_LEGACY_BUCKET_REGION`, `M4_LEGACY_BUCKET_ACCESS_KEY_ID` and `M4_LEGACY_BUCKET_SECRET_ACCESS_KEY` from the staging host's configuration. That credential must be read-only, with GetObject and ListBucket on that bucket only. It needs no database setting or key, and it copies nothing. Report its receipt's counts and set digest only.

## Daily read-only legacy refresh on staging

Approved by Khalid on 2026-11-17 (decision record "Added 2026-11-17"): read-only against legacy, no emails, SMS, push or webhooks from staging, real personal data never leaves staging, no production credentials in card workers, off the card-run path. It feeds the importer rehearsal and the pay lane's December shadow month, so it must run daily by 1 Dec.

Job: `tools/legacy-import/src/refresh-cli.ts` (`node dist/tools/legacy-import/src/refresh-cli.js`), run nightly by cron on the staging host, installed through a Hermes card. It:

- copies the legacy MySQL database into a staging database that must be named `legacy_mirror`, on a different host from the source, with one consistent snapshot (`mysqldump --single-transaction`), then drops mirror tables legacy no longer has;
- refuses to run unless the source account is read-only: `SHOW GRANTS` may list only `USAGE`, `SELECT` and `SHOW VIEW` (an allowlist; any other privilege, grant option or unreadable role grant stops it before anything is copied; a column list such as `SELECT (a, b)` counts as one privilege);
- refuses to run unless `SELECT` covers the whole source database (`` `db`.* `` or `*.*`, no column list and no partial revoke): with table-level grants the account would see only some tables, and the prune would silently drop the rest from the mirror;
- reads table names hex-encoded, so a name with a tab or newline cannot be split and pass as a different table, and refuses any name outside `[A-Za-z0-9_]` before it reaches a dump or a drop;
- names every copied table whose engine is not InnoDB in the report's `nonTransactional` list: `--single-transaction` gives those tables no snapshot, so their rows may be slightly later than the rest;
- on a target that folds table names to lower case (`lower_case_table_names` other than 0), refuses source names that fold together and compares names the same way when it prunes;
- never copies bearer-token, session or queue tables (names ending `_token` or `_tokens`, and `session`, `sessions`, `queue` or `queues`, any case), and prunes stale tables (an earlier copy of a now-excluded table included) before it copies and again after, with foreign key checks off for the drop;
- always connects over TCP (`--protocol=TCP`), so `localhost` in a URL cannot fall back to a Unix socket and reach another server;
- starts every mysql and mysqldump child (the `mysqldump --help` capability probe included) through one helper, `spawnScoped`, which always starts it with `--no-defaults` first (no `/etc/mysql`, `/etc/my.cnf` or `~/.my.cnf` is read) and gives it a scrubbed environment with an empty private HOME (no `~/.mylogin.cnf`, never the parent's credential URLs or `MYSQL_*` settings), the run's lock descriptor and the run's deadline; a test fails if any other spawn appears;
- passes passwords only through each child's `MYSQL_PWD`, discards mysql's stderr, and reports a fixed code per step, so no value, host or credential reaches a log;
- writes `last-run.json` with table names, row counts, the row total and timings only, and prints one line in the same terms; every run that holds the lock rewrites it however it ends (crashes and the deadline included), a configuration error writes it too where the path is safe (see below), and it says `running` while a copy is in progress; when a write cannot happen, the output line says so instead. A run refused because another holds the lock writes `last-refused.json` beside it instead, so it can never overwrite the owner's `running` or `ok` (a report path named `last-refused.json` is refused as `config.reportIsRefused`);
- runs one at a time under a kernel `flock` on the lock file, held by the run and every mysql child it starts and released by the kernel when the last exits, so there is no stale lock and no takeover;
- refuses when source and target are the same server under different names (`@@server_uuid`), so staging and legacy must both be MySQL;
- reads `SHOW GRANTS` for the session and `@@mandatory_roles`, so a mandatory role cannot add a write privilege unseen;
- dumps with `--set-gtid-purged=OFF` (where mysqldump supports it), so no RELOAD is needed and no replication state reaches the mirror;
- bounds every wait: each mysql session has `lock_wait_timeout=600`, the whole run has a deadline (`LEGACY_REFRESH_TIMEOUT_MS`, default four hours) after which every child is killed and reaped, and a failing side of the copy stops the other;
- never writes a report that could replace the lock file or the refusal record: every report write (configuration errors included) first refuses a report path that is the lock path through a symlinked directory, a symlink or a hard link, and a configuration error never writes to a report path named `last-refused.json`; either way it reports on stderr only. Temp files are created exclusively and never replace an existing file. The output line says `(report not written)` whenever the write did not happen. The only other files it touches are `last-refused.json`, the lock file (opened for append, never truncated, replaced or deleted) and a private empty HOME for the mysql tools.

Configuration (root-only env file on the staging host): `LEGACY_REFRESH_SOURCE_URL` (read-only legacy account), `LEGACY_REFRESH_TARGET_URL` (mirror account, `legacy_mirror` database), optional `LEGACY_REFRESH_REPORT` and `LEGACY_REFRESH_LOCK`. `LEGACY_REFRESH_TIMEOUT_MS` may be at most 2147483647 (Node's largest timer).

Reading the mirror: a consumer takes a shared lock on the same lock file (`flock --shared` on `LEGACY_REFRESH_LOCK`, the same path the job uses), then reads `last-run.json`, proceeds only if it says `ok`, and holds the shared lock until its read is finished. A refresh cannot start while any reader holds it (it exits `locked` and records that in `last-refused.json`), and a reader cannot start mid-copy, so no reader ever sees tables being replaced. Checking `ok` without the lock is not enough: the next refresh could start between the check and the read. The matrix row `REFRESH` is done: the first timer-triggered run on the #550 code (b8cd999), at 2026-11-20 00:30Z, ended `ok` with 123 tables and 865,915 rows, excluded the 7 bearer-token tables, listed no non-transactional tables and wrote no refusal record (PR #393 comment 7032910903). Before it, the 2026-11-19 repin ran once by hand with the same result (865,911 rows), over TCP with a database-wide `SELECT, SHOW VIEW` grant, and the mirror held no previously copied token, queue or session tables.

## Legacy-twin walker (verified gates)

`tools/legacy-import/src/twin` closes the release matrix's `verified` gates. For each journey it picks people from the refreshed legacy copy, reads what legacy showed them (read-only queries that follow the legacy controller, cited in each journey file), opens the same pages on staging in a real browser signed in as the same person, and compares the two fact sheets.

- A fact sheet maps paths built from fixed words, ISO dates and ids to values. Values never leave the staging host. The report (`last-walk.json`, mode 600) carries journeys, legacy person ids, counts, paths, difference kinds, decision citations and fixed codes, and `assertPrivate` re-checks every field before it is written.
- A difference is explained only by an entry in `tools/legacy-import/twin-explanations.json` citing `contracts/decisions-<date>.md` or `PR #393 comment <id>`. Anything else is a regression and keeps the gate open.
- A journey is verified when at least `TWIN_MINIMUM_PEOPLE` (default 5) people were walked, none regressed and no walk failed. A person not yet linked on the platform is a failure (`persona_unlinked`), not a skip, so verified gates move as the people and hours imports land on staging.
- `cli.js walk` runs on the staging host from a Hermes card, under `flock --shared` on the refresh lock, and refuses unless the last refresh is `ok`. It signs each person in with one session row and deletes it after their pages are read; it reaches only `https://staging.studenthub.co`.
- `cli.js walk` prints a receipt (walked revision, Kuwait month, the refresh run it read under the shared lock, and per journey its verdict, walked and distinct people, and match, explained, regression and error counts) and exits 0 only when every journey is verified (3 when one is open). The per-person report stays on the staging host, mode 600, and is never attached to a pull request.
- `cli.js close <report> "PR #n comment <id>"` runs where the report is, in a checkout of the walked revision plus evidence only. It is bound to the walked candidate: anything but `tools/release-matrix/matrix.json`, `docs/` or a `.md` file that differs from the walked revision, committed or not, refuses the close, so a new renderer, route, config or walker change means a new walk. It does not trust the report to describe itself: every journey must be one the code defines with exactly its screens, every journey the code says verifies a screen must be in the report and verified, and the minimum may not be below 5. It closes `verified` only where `built` is done, prints the receipt, each screen's outcome and the written matrix's sha256, and exits 3 unless every screen ended verified. The pull request carries the matrix change and that receipt.
- In the browser, every request and every redirect hop stays on the staging origin: the guard follows redirects itself, checks each hop before it is sent, and refuses any hop to another host or port.

Journeys: `work-history` (C-12) walks every route the screen covers: the month page `/work/history?month=` and the day page `/work/history/:date` for each day legacy shows (totals, then each session's start, end, minutes, status and manual mark). A journey must walk every route of each screen it claims, since closing the screen's gate verifies all of them.
