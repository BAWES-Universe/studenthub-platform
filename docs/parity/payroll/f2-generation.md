## Delivered boundary
`packages/payroll/src/generation.ts` is a read-only planner. It reads Work payable v1 and returns *candidates*, blocking reasons and adjustment review inputs. It never computes currency amounts, writes a line, accepts a transfer, finalizes a run or changes Work. No migrations, package/barrel/runtime changes or activation. No claim of exact-fils legacy replay or full F2 completion.

Hourly candidates group approved sessions by person/contract/period, retaining assignments and lineage. Pending/rejected/open counts are audit-only. Invalid sums, duplicate assignments/roots and mismatched scopes fail closed. The generic planner requires a **ConfirmationPort** that attests each input fingerprint. Missing port, insufficient provenance or a changed input creates no hourly candidate. Staff Generate is a separate explicit approved-hours-only action: it does not require employer month confirmation. Its scoped adapter records `staff-explicit-range/v1` against the exact approved Work input as action provenance, never as employer approval. Real authorization and a coherent Work/rate snapshot are still required; this marker supplies neither.

Weekly salary candidates select active, undeleted-person, auto-generate monthly contract snapshots effective on the supplied Kuwait business date. Every company is visited; parent company groups where supplied. The window is today minus six days through today and payoutDivisor is 4. F1 must supply an immutable rate revision and value it with legacy policy. Non-KWD snapshots are blocked rather than silently relabeled. This does not calculate hourly/monthly/fixed amounts or introduce calendar-proration policy.

Complete existing person/contract/period claims exclude duplicates, including manual lines. Complete finalized roots are resolved outside the period, including moved or discarded sessions. They never appear in an ordinary candidate: Finance gets a review input referencing the cumulative recognized revision. No delta is written or applied here. An unknown root is blocked, not treated as zero. Before-finalization regeneration is only another preview, not mutation of a staged transfer. Identical/reordered inputs give stable keys; a database constraint and atomic recheck are still mandatory.

## F1 and F3 interface needs
- F1 adapter: value each candidate using authoritative rate resolution/rounding; emit PayLineDraft with canonical decimal totals, store grouping, immutable rate/confirmation/session/root provenance. Null Work contract means the manual-rate path still needs explicit valuation; no invented rate.
- F3 transaction: reread/revalidate source versions, confirmation status, claims including manual lines, and finalized ledger before atomically reserving the person/contract/period and lineage keys and appending ALL lines. A stale preview, conflict or late failure must persist zero lines. F2 candidates are not authority to append without these checks.
- Corrections: price current lineage with F1, compare to cumulative recognized amount (original plus finalized adjustments), emit only net new adjustment into an open cycle, reserve adjustment revision once. Do not rewrite prior finalized transfer/workbook; unchanged valuation owes zero. This planner intentionally does not invent monetary adjustment amounts.
- Caller supplies authorized source scope, complete claim/recognized ledgers and coherent snapshots. No endpoint, authorization adapter or scheduler is supplied in this slice.

## Atomic generation protocol (pure service, no persistence adapter)
`generation-transaction.ts` adds `commitGeneration(store, command)`. The caller sends actor/target/version and preview key+revision, not line values. One required transaction scope performs: current authorization + target lock; receipt lookup/replay; authoritative locked rebuild with actual F2/F1; exact revision check; refusal of blocked/empty/adjustment-bearing plans; identity reservation; draft append; durable receipt. Any thrown failure must roll back claims, lines, audit and receipt together. Finalization is absent.

Seven new disposable transaction-double tests exercise commit/retry without another rebuild or append, changed snapshot, missing confirmation, claim/partial-line/receipt failures and successful retry, preexisting manual claim, current authorization before replay, changed retry revision, and refusal to append finalized adjustment reviews. These validate service sequencing and its adapter contract only; they are NOT PostgreSQL atomicity, lock/concurrency or durable idempotency evidence. Total:23 passing synthetic F2 tests, strict scoped compilation.

Concrete persistence gap: F1 `appendLines` currently starts its own transaction, so it MUST NOT be nested as this protocol's appendDraft. A persistence owner must expose a shared-client F1/F3 unit of work preserving existing staff authorization, draft-only/version/currency/assignment checks and audit; lock/revalidate Work/rate/confirmation snapshots; reserve globally unique person+contract+period identities including manual entries and cross-period finalized roots; store a unique target/batch receipt in that same transaction. Race/rollback tests on disposable PostgreSQL are still required. This slice creates no competing store, migrations or employer-confirmation policy and cannot be wired to real generation yet.

## Durable adapter follow-up (local only)
Dependency: F1 PR #545 at `b8c3febcbcea3bdf1e3e55f8335a4727f6a312f3`. Its domain, DB store and migration0550 were compared byte-for-byte with the supplier used here. A separate small follow-up seam extracts the unchanged F1 write body into `appendLinesInTransaction(client,...)`; the existing public wrapper still owns its own transaction. This does not alter the F1 narrow publication packet. F3 has **no product dependency**: generation only appends drafts, does not invoke lifecycle/billing and shares the same parent lock. Migration0556 is disjoint from F3's0562; confirmed with its helper.

`PostgresGenerationStore` now implements the protocol with a required current-authorization policy and transaction-scoped rebuild callback. It stores globally unique person/contract/period claims, global lineage-root reservations and target/batch receipts atomically with F1 lines and audit. Parent authorization/lock precedes replay; receipt replay is evaluated after reauthorization and before the draft rebuild/write path; the combined F2/F3 PostgreSQL acceptance should verify replay after a real lifecycle lock, not a fixture-only status update. Person-wide advisory locks are shared with a line-write guard so ordinary F1/manual inserts participate; roots are reserved in globally sorted order. Claims, root reservations and receipts are retained with row-level update/delete and statement-level truncation guards. Cancellation or deletion does not release claims or permit automatic regeneration. A replacement requires an explicit Finance-approved reissue or adjustment contract; no such action exists in this slice. No authoritative production snapshot rebuild is supplied.

Ambiguous manual provenance is an explicit conservative blocker: existing unknown-contract or same-contract rows in overlapping periods prevent generation; declared manual roots also conflict across periods. Conversely manual inserts cannot bypass an existing overlapping claim. This is not full manual-pay parity or a claim that older rows without root provenance can be matched across disjoint periods. A production rebuild must reject unresolved historical roots/claims. Note-only edits and paid-flag changes with unchanged amounts/calculation are not rejected by the new guard. No guessed manual claims are created.
