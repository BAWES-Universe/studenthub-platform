## Summary — ten highest-value frontend-only findings

1. `GET /aws/config` is unauthenticated on the server (`AwsController.php:15`) and the client builds a browser S3 client from the returned static key/secret, uploading `public-read` objects (CAND-FO-19) — wider than SHU-134.
2. `/change-password` posts to `/account/update-profile-url`; passwords are never changed and `profile_url` is wiped (CAND-FO-33).
3. Job eligibility (age/gender/availability) is enforced nowhere — not in the UI, not in `JobController::actionList` (commented out) — and apply does not check the job is active (CAND-FO-01/02, RC-F1/F2).
4. `internal_note` is serialised to candidates by `/requests/interview-requests`; the UI just doesn't render it (CAND-FO-14, resolves RC-F6).
5. Clock-in/out geolocation is required only by the UI; the server accepts calls without coordinates and clock-out overwrites the start location (CAND-FO-09/10, WK-F1).
6. Manual work log: no start<end, future-date, overlap or open-session validation on either side; `total_time` can be negative; client sends UTC-shifted dates (CAND-FO-12).
7. reCAPTCHA v3 tokens are collected on five screens but verification is commented out on every server action (CAND-FO-22).
8. Bearer token plus the full profile (IBAN, civil id, phone, coordinates) persist in `localStorage['state']` and are not cleared on logout (CAND-FO-26); civil-ID images are rendered from a public bucket URL (CAND-FO-18).
9. The repo commits an Android release keystore, Play upload key, a Google service-account private key, a TLS private key, a Sentry auth token and a Redis dump (CAND-FO-38).
10. Client and server disagree on "profile complete"; the client polls `unread-count` every 3 s; delete-account and 2FA toggle need no re-auth; several routed screens are stubs or call missing backend routes (CAND-FO-15/30/31/32/35).
